# 本机持久摘要任务：API 与阅读器入口

本阶段在持久摘要 API 基础上接入阅读器提交、进度、取消与显式接收结果。仅支持正在运行此页面的本机 Node bridge；没有手机配对、远程执行或云端执行。验证包含 DOM 与实际本机 HTTP bridge 加假 provider，不包含真实 GUI、原生 macOS 运行或真实订阅模型质量/额度验收。

仍复用 Node 轻量 bridge、`reader/summary.js` 的全文分批和引用校验，以及现有 `providers.ask` 官方 CLI 适配。Python `ImportJobs`、前台问答、翻译、原有停止语义均不迁移。独立阅读、笔记和搜索不需要任务执行器；任务存储异常也不会阻止本机阅读页面和原有前台接口启动。

## 明确的执行边界

- 原 `/api/ask` 属于前台请求，HTTP 连接关闭会终止其 request signal。阅读器现有分批停止流程不变。
- 新 `/api/v1/tasks` 是明确提交后台摘要：完整请求验证并持久化之后才确认接收。随后页面关闭、网络断开或取消客户端 fetch，不表示取消任务。
- 只有显式 `POST .../cancel` 请求取消任务。退出执行器、应用被终止或电脑离线不是用户取消，也不会触发自动重做。
- 当前只监听 `127.0.0.1`。现有 Host、Origin、Fetch-Site、JSON、CSP 边界保留；没有对 localhost 开放远程访问、relay、配对、凭据或云端执行器。
- 实际模型调用仍使用本机已登录的 Codex / Claude Code 订阅，不能推断模型在本机 GPU 上运行。账户可用性及剩余额度不会因 task API 就绪而得到验证。
- 仅任务队列内部串行执行；它与原前台请求共用原 provider 排他约束。遇到正在使用的 provider 会失败并保留状态，不偷偷重试或额外消费额度。

`npm run dev` 在当前源码目录的 `.coconut/dev/tasks` 保存开发任务；源码 CLI `node desktop/server.mjs` 在当前用户 `~/.coconut/tasks` 保存任务；原生应用使用 `app.getPath('userData')/tasks`。三者是独立目录。程序调用 `startBridge` 需要显式 `taskDirectory` 才启用任务，测试使用临时目录。只探测健康、能力或读取任务不启动模型；页面加载客户端 helper 不会发送模型请求；已有任务关联会自动查询状态，查询本身不调用模型。

## v1 接口

这是第一个有版本标识的窄接口，后续扩展不应让客户端依赖额外未知字段。协议版本与磁盘格式版本分开；HTTP 协议仍为 1，磁盘 ledger 与浏览器关联格式为 2，兼容读取格式 1。

- `GET /api/v1/executor`：`protocolVersion`、执行器类型和在线状态、`supportedTaskKinds`、`enabled`、队列限制和取消/重启语义。提供商分别声明 `supported: true`、`availability: "not_checked"`，不把支持与已登录可执行混为一谈。当前 `remoteSubmission: false`。
- `POST /api/v1/tasks`：新任务返回 202 和 `{protocolVersion, created: true, task}`；重复提交相同意图返回 200、原 taskId 和当前状态。
- `GET /api/v1/tasks`：最多 128 条未归档任务的元数据列表，不附全文或结果正文。
- `GET /api/v1/tasks?archived=true&limit=20&after=...`：归档元数据页，默认 20 条、最多 50 条，返回 `total` 和 `nextCursor`。按 taskId 排序，cursor 为上一页末尾的 taskId；不是快照隔离列表，并发归档/恢复后可刷新首页。
- `POST /api/v1/tasks/{taskId}/archive` / `restore`：请求体 `{ "protocolVersion": 1 }`，显式归档或恢复原任务到当前列表，不执行模型。重复操作幂等。
- `GET /api/v1/tasks/{taskId}/export`：完整救援记录，包括原 idempotencyKey/inputDigest/taskId/attemptId、完整 snapshot 和结果。只读，不删除或创建任务。
- `GET /api/v1/tasks?submissionKey=...`：跨未归档与归档记录按原幂等键查找；任务不存在时 `task: null`。用于 taskId 回执丢失后的确认。
- `GET /api/v1/tasks/{taskId}`：任务状态、进度和成功结果，完成结果含完整原文快照和引用。
- `POST /api/v1/tasks/{taskId}/cancel`：请求体 `{ "protocolVersion": 1 }`。排队任务直接取消；运行中任务先保存 `cancel_requested`，再触发 provider abort。取消请求重复发送不会产生新执行。

提交结构：

```json
{
  "protocolVersion": 1,
  "kind": "summary",
  "idempotencyKey": "one-explicit-user-intent",
  "document": { "key": "document-key", "revision": "document-lifetime-and-input-revision" },
  "provider": "codex",
  "consent": true,
  "segments": [{ "id": "cue-1", "text": "完整原文……" }]
}
```

`consent` 必须来自对这个后台执行意图的明确确认，不能沿用现有前台按钮的同意。UI 展示全文范围、分批数、所选提供商、最多请求次数、订阅额度与离页后继续执行的说明。模式切换撤销原同意，沿用同一份确认勾选，不增加第二层确认。后台文案不沿用前台停止语义。

客户端应先可靠保存幂等键、文稿 lifetime/revision 与提交输入，再发送。超时、网络错误或 5xx 可能发生在接收已经落盘之后，先按原 key 查询，不要生成新 key 重做。找不到时，只能重发原 key 和原 payload；后到的原请求仍会被同一个 key 去重。相同 key 配不同 revision、provider 或原文返回 409。API 不自动重试任何模型请求。

每个新意图有稳定 `taskId` 和单个 `attemptId`。当前没有 retry/resume 接口，也不会在重启时增加 attempt。若用户在核查中断/失败后决定重新执行，需要新明确意图和新 key，可能再次消耗额度。

## 状态与持久化

状态：`queued → running → succeeded / failed`。显式取消为 `queued → cancelled` 或 `running → cancel_requested → cancelled`。

取消回执区分接受请求与执行收尾：运行中返回 `cancellation.executionSettled: false`；provider 的 promise 收尾后记为 true。取消之后无论 provider 迟到返回成功或失败，都不再接收其结果。`cancelled` 表示此任务不再接收结果，不保证外部提供商没有已完成请求或已消耗额度。

- 每次提交、开始执行、批次进度、终态和取消请求都通过串行队列写入临时文件，fsync 后原子替换 manifest，再同步目录；成功写入后才确认接收或继续下一批。
- task 状态与客户端连接独立。进程内取消信号只归执行器拥有。
- 启动读取遇到 `queued` 或 `running`，统一转成 `interrupted`；上次可能已经发送的请求结果/额度未知，绝不自动重新发起。`cancel_requested` 恢复为取消终态，保留执行结果未知说明。已经完成的结果保持可查询。
- 写入失败使任务子系统停止接收/执行并 abort 当前信号；不声称结果已保存。损坏、不支持版本或超过上限的 manifest 不覆盖、不推理，任务能力降级为不可用，阅读仍可使用。
- 目录内仅允许一个在线 writer。进程锁保存 PID 和随机 token；确认原 PID 已退出后才恢复。死锁恢复步骤本身的异常/残留恢复锁会保守阻止恢复，需人工检查，不冒险启动第二个 writer。PID 被复用可能导致保守拒绝。
- 文件以 0600 创建，目录新建为 0700；明文存储在用户自己的磁盘，不是加密保险库。最多 128 条未归档任务、2048 条归档任务、8 条未结束任务，共用 32 MiB manifest；每条活动任务按不可变输入之外另保留 1 MiB 终态/结果预算，接收前检查全部活动任务的预算，防止接收成功后因状态增长、取消或最终摘要而无法落盘；不静默删除旧任务或幂等记录，满额时拒绝新提交。提供显式终态归档与恢复，归档只释放未归档条数名额，不释放字节或自动删除数据。
- 每条任务只持久一份原文快照、文稿 key/revision、provider、摘要意图 digest、状态/时间/进度及最终结果。不保存阅读笔记、音视频、文件路径、账号凭据。中间批次摘要仅在内存中供同一轮汇总；重启后不复用中间结果，不继续消费。

批次数与内容上限直接复用 `Summary.plan`：最多 20,000 段、1,000,000 字符、64 个原文批次加 1 次汇总。新任务 HTTP body 上限 8 MiB，原前台 API 仍保留 1 MiB 上限。计划及最终引用必须通过现有摘要校验。

## 客户端与文稿隔离

`reader/task-client.js` 提供 `submission`、`createClient`、只读 `matchesResult`、复制回执的 `resultFor` 和独立救援包 `recoveryFor`。它没有轮询、重试、写入书架、取消前台或自动发起请求的副作用。测试中的新 client 模拟刷新后重连。

`resultFor(task, document, revision)` 只在成功结果的文稿 key、lifetime/revision、完整 cue ID/原文顺序和文本都一致时返回一个结果副本，否则返回 null。它从不改写文稿。UI 接受结果走现有存储回执流程，在同步追加历史前再次检查 owner/revision/完整原文；储存失败明确提示仅在此页，允许使用既有保存重试或备份。原文、译文、笔记和既有 AI 历史不会被任务快照覆盖。相同 key 被移除后重新导入是新 lifetime，不能复用旧 revision。

## 阅读器中的最小流程

1. 打开整篇摘要入口。执行方式默认“前台分批”，原有收起、离开、停止后续批次和继续摘要语义保留。
2. 选择“本机后台”。客户端只读取能力和已有任务；检查协议 v1、本机执行器、summary 能力、断连继续、取消与重启语义。协议不兼容、任务存储异常、非本机页面或失联时，后台提交不可用，阅读保留。
3. 核对完整范围、批次数/请求上限、提供商和额度说明，勾选当前范围后提交。不把支持的 provider 或在线接口当成已登录、尚有额度的证明。
4. 可收起、切换文稿或关闭页面。本篇摘要有“查看本机后台任务”入口，书架中有折叠的任务区。提交成功保留任务关联，刷新后查询原任务；状态轮询不依赖面板展开。应用/执行器退出仍会中断，不能宣称 app 退出后仍在处理。
5. 任务完成后在条目中查看正文和引用；打开原文稿，点击“接收至当前原文稿”，才追加到其摘要历史。原文改变、文稿移除/重新导入、其他文稿或已取消任务不能接收。重复点击/刷新不会重复追加。

## 客户端关联与恢复边界

`reader/background-summary.js` 使用本浏览器独立的有版本关联记录。提交前先通过既有书架存储回执保存文稿本地 lifetime，再持久保存幂等键、provider、revision 与完整发送输入，之后才发送。任一步落盘失败即不发新任务。终态结果正文不复制到该关联记录；它保存在执行器上，成功查询后供预览和显式接收。

- 关联最多 128 条未归档与 2048 条归档记录；浏览器 quota 达限或损坏会保留原记录并阻止新提交。提供显式归档与恢复，没有永久清理或跨浏览器同步。关联包含原文，明文留在此站点的浏览器存储中，不是凭据保险库。
- 书架普通 JSON/全书架备份导入会剥离本地 lifetime 和已接收 taskId 标记；重新导入不会继承旧任务所有权。书架本身的刷新和既有 IndexedDB/legacy 存储加载保留这些本地字段。
- 丢失回执或 5xx/网络异常先用原 key 查询；不会换 key 自动重做。查不到时提供显式“重发原提交”，只用原 key/原 payload，且原文稿/范围仍须一致。失败/执行器中断没有自动 retry/resume。
- 取消是独立动作；撤销勾选、收起、切换和 fetch 断开不是取消。丢失 taskId 时仍可按原 key 请求取消。取消意图先保存，不接收迟到结果；较早开始的查询或取消回执不能覆盖较新状态。重发前在异步查询之后重新检查取消、文稿、原文与存储闸门；中途取消/编辑/移除即不再发送。若取消到达前任务已完成/失败/中断，显示真实终态及已放弃接收，不永久显示等待执行收尾。未确认取消会明确提示继续查询/取消。
- 其他本机任务可查看状态并显式取消；已发现的活动任务会继续只读轮询，离页停止查询，返回后重新查询。本浏览器没有原提交关联时，不可把结果接收进任意当前文稿。清除站点数据或更换端口后需要保留这一限制。
- 同一浏览器地址切换任务目录（例如在默认 `8080` 端口切换源码 CLI 与 `npm run dev`）时，某个已知 taskId 的明确 `404 / not_found` 只标记该条“此执行器找不到”，保留原 taskId、提交输入与取消意图；不把健康执行器误报失联，也不挡住它的其他任务及新的显式提交。不自动重发旧意图、不将同文稿的其他 taskId 认领为旧结果；原任务接收与取消入口暂不可用，切回原服务刷新后恢复核对。新提交是独立任务，原请求可能已消耗额度。网络错误、5xx 或无法识别的 404 仍按连接异常处理，不推断任务不存在。
- 清除站点数据、换浏览器或端口后，只要原执行器任务目录仍在且服务可读，打开「书架 → 本机后台任务 → 刷新」，在成功任务中点「查看独立结果」。列表不预先下载全部原文；点击后才读取该 taskId，核对协议、任务身份、成功状态、完整快照和引用。正文立即展开，可查看最多 8 条提交时的引用原文预览，每条最多 1,200 字符；完整原文由下方「下载独立结果 JSON（含原文）」保留。任务标识、原文稿标识和提供商一起显示，不能靠相似文字认领当前稿件。
- 独立 JSON 使用 `format: "coconut-background-summary-result"`、`version: 1`，包含 taskId/attemptId、原文稿 key/revision、提供商、时间（有记录时）、摘要正文、引用和完整 ID/文字快照。不伪造时间轴，不包含阅读笔记、媒体、幂等提交键或本地接收标记；它供独立核查留存，不能作为书架备份导入，也不恢复原文稿所有权。下载提示只说明已发起，请确认文件确实保存。
- 仍有关联但原文被删除、修改或重新导入时，也可查看和下载原成功结果，接收限制不变。保存的取消意图仍会隐藏其结果接收与导出入口。损坏的浏览器关联记录不会阻止其他本机成功任务的只读取回，也不会被救援覆盖。失败、取消和活动任务不提供结果导出；查询失败可显式重试读取，绝不重跑模型。过期查询若遇到任务从列表消失或身份/状态变化，不会展示旧响应。
- 关联存储采用读取后比较和写入回读，发现其他页面更新则阻止后续提交/接收并要求刷新。它不是跨进程原子 CAS，也不宣称跨设备并发协调。正式多端配对与强一致协调仍未实现。

## 显式终态归档与救援

在「书架 → 本机后台任务」中，对已完成、失败或已经确认执行收尾的取消任务点击「归档任务（保留原文与结果）」。正在排队、执行、取消等待收尾、中断或结果未知的任务不可归档；重启得到的取消终态若没有 `executionSettled: true`，也不可归档。归档动作不等于取消、接收摘要或重新提交。

「已归档任务」每页最多展示 20 条，可刷新首页、翻到下一页、按完整 taskId 精确查找并读取结果、下载完整救援 JSON，或「恢复至当前任务列表」。恢复保留 taskId、attemptId、幂等键、digest、原文稿 revision 与原文，不发起模型请求。恢复后仍须原稿 lifetime/revision/原文一致才能显式接收；已接收标记不重置，修改稿或重新导入的副本不能接管。没有关联的任务只能独立查看与导出，恢复也不创建关联。「查看本浏览器归档关联」另以每页最多 20 条核对本地保留的原 taskId；切到其他任务目录且服务器归档为空时自动显示此页，明确标记找不到的原记录，切回原服务即可再核对，不让原关联从界面消失。

- `tasks.json` 的一个 `tasks` 数组保存全部原记录，只新增/移除 `archivedAt` 标记；不在两个文件之间搬迁。每个变更仍通过同一队列、临时文件 fsync、原子 rename、目录 fsync 提交。rename 前中断留下旧完整版本；rename 后中断留下新完整版本。遗留临时文件不参与恢复，不自动清理用户证据。磁盘写入失败停止任务子系统，客户端只应重查原任务，不推测是否提交成功。
- 查 taskId、查原提交键和重复 submit 均搜索所有记录，包括归档；相同键与不同输入仍返回 409。归档没有重复执行或丢失幂等记录的捷径。
- 条数满返回 `active_tasks_full`（128 未归档）或 `archive_full`（2048 已归档）；实际 JSON 加未结束任务预留超 32 MiB 返回 `store_full`。归档不能释放总存储字节，字节恰好满时新增归档标记也可能被拒绝。没有自动淘汰、无限容量、压缩保证或性能容量承诺。2048 是明确的实现上限；浏览器实际 quota 可能先到达，完整输入长期保留也占其空间。导出不会释放本地容量。
- 浏览器使用同一个 localStorage envelope 原子保存两类关联，归档不删 owner/lifetime/revision/payload。服务器与浏览器不构成分布式事务：先请求服务器，再保存关联；任一回执丢失或本地 quota 失败，都保留原关联，刷新按原 taskId 查询服务器真实状态收敛。若浏览器保存仍失败，先保留原数据、解决空间问题并重载；不要新建提交键。归档页的迟到回复不能覆盖更新的恢复操作；操作回执还会废弃此前开始的读取，等待已在途刷新后发起新的只读核查。
- 完整救援下载为 `format: "coconut-background-task-recovery"`、`version: 1`；内含 `coconut-background-task-record` 和（存在时）本浏览器原关联。它比独立摘要结果 JSON 多保存幂等身份及完整终态记录，可能包含完整原文，应作为私有备份保存。本版不提供导入、跨机器恢复任务执行或文稿所有权接管；「恢复」仅指回到当前任务列表。下载失败不会更改执行器记录，成功提示也只表示已发起下载，请确认文件保存。

### 版本迁移与回滚

新版读取 v1 不立即改写原文件；下一次成功持久化（含正常关闭保存）写成 v2，保留全部任务和未知扩展字段。浏览器关联下一次成功保存也升级为 v2。旧版遇到 v2 会保守拒绝读取该任务存储/关联，仍保留原始数据；不会自动删归档或降级版本号。因此降级软件前应退出执行器并备份任务目录及浏览器站点数据，保留新版环境用于查询/导出。不要把 v2 的版本号手改成 1，也不要把备份覆盖在仍有新任务的目录上；没有无损反向迁移或合并工具。

### 归档验证边界

定向 Node/HTTP/DOM 验证覆盖 128 条终态后归档再提交第 129 条、2048 归档上限及有界分页、恰好字节满拒绝、跨归档重复键/重复ID损坏拒绝、v1未知字段保留、原身份完整导出、恢复不消费、取消未收尾/中断拒绝、浏览器配额失败与丢回执重查、旧分页响应竞争、原稿修改后拒接收。真实子进程在 rename 前后暂停并 SIGKILL 验证重启只读到一个完整版本；写入 ENOSPC 为受控注入，不是实际填满磁盘或断电耐久性测量。

现有 GHA 专用 `background-summary-browser.mjs` 增加真实点击归档、窄屏按钮可达性、原生救援下载、服务重启/reload、恢复与原关联/接收历史保留旅程。作者仅运行 CPU/DOM/HTTP 合同与脚本语法检查，没有本地运行 Chromium、Electron、macOS 或真实模型；真实 GUI 结论须以精确交付 commit 的 Browser acceptance 为准。

# 长文摘要计划

打开文档、查看计划和恢复备份都不会发出模型请求。先连接本机已登录的 Codex / Claude Code，查看范围和请求次数，再勾选订阅发送确认并点击发送。

## 范围与额度

- 计划覆盖当前文档全部原文，不受搜索、摘录、笔记筛选影响；局部提问仍保存为问答，不会冒充整篇摘要
- 每份计划最多 20,000 个原文片段、1,000,000 个 UTF-16 字符、64 个原文批次，原文和 ID 的序列化记录另有 2,200,000 字符上限。多个限制同时生效，过大时明确拒绝并建议拆分
- 每批最多 400 段、16,000 个原文字符，序列化的原文片段最多 48,000 字符。超长单段按连续字符范围拆分，不漏掉原文，不拆开 Unicode 代理对；引用仍指向原片段，不能声称是逐字定位
- 一批可直接返回整篇摘要；两批及以上必须再进行一次汇总，首次完成总计不超过 65 次请求，明确确认后的手动重试另计。每次串行执行，无自动重试、付费 API 回退或购买额度
- 范围提示说明原文、后续分批笔记和引用将发送给选中的提供商。阅读笔记、音视频和其他文档不会发送。精确 token 用量、剩余订阅额度和运行时间无法事先保证

## 分批与汇总

`reader/summary.js` 是无网络、无模型调用的确定性计划和校验模块。页面通过现有 `/api/ask` 同源、明确 consent 的接口逐批发送，因此 Node 和可选 Python 服务沿用原有官方 CLI 安全限制。

分批只产生未核对的中间笔记，每份最多 1,200 字符和 8 个有效原文引用；笔记与引用另受序列化上限约束，以确保最坏情况下汇总仍在既有 250,000 字符请求限制内。空回答、缺引用、错误 ID、过长或不完整输出全部拒绝，不悄悄截断、不自动重试。

只有所有原文批次都成功并保存后，才把全部中间笔记发送给一次汇总。汇总返回的批次引用会映射到这些批次已验证的原文引用，最终引用不是虚构的 batch-ID。页面及 Markdown 导出明确说明这是“批次依据”：它们帮助回源核对，不能证明每句话都有独立支持，也不能保证模型没有遗漏。

完整原文快照、提供商、分批数、汇总次数和引用随最终摘要保存。原文编辑、添加、移除或重排都会使原有摘要过期；长文快照在 JSON 导出、导入和刷新后仍保持完整。

## 停止、关闭与恢复

每次请求前先保存完整计划与正在请求的位置；每批响应通过校验后先保存，再开始下一批。无法保存时停止后续请求，不能把仅存在当前页面的结果标成已保存。

“停止后续摘要批次”允许当前请求结束并保存，但不会启动下一批。切换提供商、任务、文档、关闭 AI 面板或修改原文也会阻止后续批次。已经发出的请求可能消耗额度，不能撤销。

分批进度放在文档的 `summary_job`，因此随浏览器书架和文档 JSON 备份保留。刷新或重启时不会自动继续；原来正在执行的请求会标为中断。若服务已处理但响应丢失，重试可能重复消耗该批额度，界面明确提醒。重新确认后从第一个未保存批次继续；若仅汇总失败，则只重做汇总。

原文或提供商改变时，不得把旧分批用于当前摘要。用户必须明确放弃旧分批进度再规划；已有的历史完整摘要仍保留并显示是否过期。所有批次加最终汇总完成前，不生成完整摘要，不用本地摘抄补位。

## 验证范围

单元、DOM 和 Chromium 验收使用自写模拟原文与注入的提供商响应，不调用真实 CLI 或模型，不使用真实订阅额度。覆盖边界、无损分批、引用追溯、整篇快照、保存失败、停止、提供商及原文变化、中断恢复、导出/导入和最终汇总门槛。

这些测试证明流程与结构约束，不证明真实长文摘要的准确性、完整性或可读性。真实提供商和质量验收需要另行明确授权与实际样本。
